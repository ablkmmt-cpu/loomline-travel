# 第一层 · 地基（先做，优先级最高）

## 1.1 技术架构：无框架下的维护方案

**现状问题**：纯手写静态站，21+ 个 HTML 页面各自独立，改导航/页脚/统计代码要逐个改文件；没有统一模板。

**方案 A（立即执行，零构建）——共享片段 + 打标脚本**
```
components/head.html      ← 统一 <head>（字体、meta、统计代码、OG 标签）
components/footer.html    ← 页脚、隐私弹窗
components/analytics.js   ← 埋点
tools/stamp.mjs           ← 扫描页面中的 @@HEAD@@ / @@FOOTER@@ 标记，批量替换
```
- 改 1 个文件 + 跑 `node tools/stamp.mjs`，全站同步
- 对 AI 代理（Codex 等）友好：只改组件，脚本负责扩散
- **立即解决埋点、OG 标签、品牌信息三件事的批量维护问题**

**方案 B（中期方向）——迁移 Astro 静态站点生成器**
- 组件系统（导航/页脚/头部各一个组件）、数据驱动页面（10 城 = 1 份数据 + 1 个模板）、Markdown 写攻略
- 输出仍是纯静态 HTML，部署方式不变
- **时机**：随"目的地迁入标准产品"一起做（页面本来就大改，正好迁移）

**不推荐**：React/Vue SPA（对本站过重，且引入 SEO 风险）。

## 1.2 分析埋点（P0，可立即投喂 Codex）

完整提示词见 `previews/codex-analytics-instrumentation.md`，核心：
- **GA4 + Meta Pixel + TikTok Pixel** 全站接入（新建 `assets/analytics.js`，各页只加一行 `<script>`）
- **6 个统一事件**：`whatsapp_click` / `email_click` / `service_click` / `form_submit` / `form_submit_success` / `form_submit_error`
- **UTM 采集**：社媒来源归因（sessionStorage 防站内跳转丢失）+ 表单 6 个隐藏字段随询盘发出
- 上线前需人工替换 3 个真实 ID（GA4 / Meta / TikTok），并把 6 事件标记为转化

**为什么必须第一层做**：没有埋点，第二、三层所有改动都无法评估效果，等于盲改。

# 第二层 · 页面与模块（定结构、动页面）

## 2.1 产品体系重构：标准产品 vs 定制产品

**目标信息架构**：

```
首页
├─ 标准产品（原目的地页 + 原 Classic/Self-Guided 归并）
│    ├─ 成都系列（成都+熊猫 5D4N / 成都+九寨 6D5N / …）
│    ├─ 北京系列（北京经典 4D3N / …）
│    └─ …（10 城逐城铺开）
│    └─ 每页底部：升级定制通道
├─ 定制产品（原 Custom Tour，强化"标准可升级"）
├─ 体验产品（7 个体验保持，作为标准产品的增值模块）
└─ 联系页 /contact.html（所有 CTA 的最终落点）
```

**目的地页迁入标准产品的可行性结论：可行，分批做（试点 → 铺开）**
- 优势：价格可见→询盘质量提升；模块复用→运营标准化；标准→定制升级路径清晰；产品式 SEO 更好；可接行程引擎"24h 自动出初稿"
- 风险与对策：
  - 定价敏感 → 只给区间价 + 按酒店档位分级（见预览 02）
  - 内容量大 → 先做成都 + 北京两个试点，跑通再铺开
  - 失去攻略型流量 → 攻略内容保留为产品页下部"旅行指南"分区
- 预览：`01-services.png`（首页双产品卡）、`02-standard-product.png`（产品页样板）

# 排期与依赖

```
第一层（1~2 周）
  ├─ 1.2 埋点：Codex 提示词投喂 → 验收（最优先）
  └─ 1.1 架构：components + stamp.mjs → 全站套用
  └─ 1.3 基建：OG/meta 模板、品牌资产

第二层（3~6 周）
  ├─ 2.1 产品体系：信息架构定稿 → 成都+北京试点产品页
  ├─ 2.2 首页：Services/Destinations/表单/FAQ/信任 逐模块上线（验收各预览图）
  ├─ 2.3 /contact.html + 标准产品模板 → 内容中心启动
  └─ 2.4 模板统一（随第一层组件化自然完成）

第三层（贯穿，7~8 周起收尾）
  ├─ CTA 参数统一、mailto 清理
  ├─ 品牌名/邮箱统一
  └─ OG/schema/sitemap/性能 上线
```

**依赖关系**：第一层必须先于第二层（埋点度量效果、组件化降低改动成本）；第三层可并行，但建议在页面稳定后统一打磨，避免返工。
